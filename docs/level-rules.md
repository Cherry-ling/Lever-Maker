# 关卡规则文档 v0.1（草案）

> 状态：**元素/地形对齐 + 参数区间核对全部收口（2025-06）**。基础规则 + 全部特殊元素已定稿；制造机多格尺寸判据已拍板（判据 C，见 §2）；门 Door / matchBlockOrder / hasCat / 钥匙 / 星·猫 / 绑定×箭头 = 用户暂不管。452 关语料统计见 §6。源码证据与差异见 `level-rules-vs-repo.md`。
> 用途：This doc 是 AI 编关工具、关卡编辑器、游戏引擎三方共用的规则依据。

## 0. 目标（已确认）
- 已有游戏成品；本工具是 **AI 编关工具**
- 核心质检 = 可解性验证 + 难度评估（BFS 求解器、最少步数）
- 输出关卡格式须与现成游戏兼容 [待拿到样例]

## 1. 基础玩法规则（已确认部分）
- **棋盘**（已确认）：由**任意形状的格子集合**定义（**非固定矩形**，可带凹角/异形/L 形棋盘等）；**尺寸不固定，随关卡区间/难度变化**；**有边界**（边界阻挡）
- **棋子**：按颜色分组，同色可多次出现（即同色多对）（已确认）；每组(颜色)数量范围 [已核对语料：中位 4、常见 2–6、全区间 1–28；每关颜色数中位 7、常见 5–8、全区间 1–10，见 §6]
- [已确认] **移动（拖拽跟随，不是滑行）**：
  - 选中后，棋子/绑定簇随指针拖拽；`MoveAbility.TryMoveTo` 每次最多推进 0.5 格（手动制造机预览为 1 格），并以 `ClusterPlaceable` / `PosPlaceable` 校验目标锚点。
  - 占格、cells 范围、墙、门、颜色筛选、区域锁与逻辑层共同决定可放置性；`BOTH` 可先尝试横向、再尝试纵向，`VER` / `HOR` 只允许相应轴。这里没有滑行惯性，也没有“沿一条直线滑到被挡才停”的规则。
  - 每次成功更新到一个格位后都会调用结算；松手时会再结算一次以覆盖最后一帧。因此它是“拖拽中的当前格位结算”，不是预先扫描经过路径，也不是仅在开始选中时结算。
- [已确认] **消除 / 消耗结算**：
  - 拖拽中每次成功更新到可放置的当前格位，都会由 `ResolveImmediateDragInteractions` 立刻检查并结算；松手时仅再复查一次，覆盖最后一帧未触发移动结算等情况。同一次结算至多消费一个目标，优先级为 **Door → IceShaver → ColorTrain → 普通色块**。选中瞬间不会因起点已相邻而自动消除；未移动就松手时仍会走一次当前格位结算。
  - 普通色块要求可见的四邻格相接（双方 `GetUnprotectedGirds`）、逻辑色相同、同一玩法逻辑层、双方可移动且可匹配；并拒绝 StepLock / KeyLock / Lock / Floor / Immune、全冰覆盖、制造机预览块等状态。`withStar` 的现码为：**发起拖拽的块**带星要求目标也带星，是否应当双向对称 [待确认]。
  - 满足条件时仍是两枚实体成对消除；多格块的任一未保护格相邻即可令整块作为一个实体消除。不存在“路径中第一个相邻瞬间”或“起点相邻立即消”的独立规则。
- **消除后棋盘**（已确认基础规则）：**不自动填补**，保留空位（特殊地形可打破该规则）
- **匹配事件流**（已按仓库修正，供特殊元素各自订阅）：普通色块匹配、IceShaver、ColorTrain 等会发出 `Block.Event.BLOCK_MATCH`，但每个机制有自己的筛选条件，不能笼统视为“任意消除都统一扣血”。
  - DecorationArea：只接受普通双块、ColorTrain、以及指定 IceShaver 事件（见 §2）。
  - 冰区：每个 `BLOCK_MATCH` 都令每一片存活冰区 -1（见 §2）。
  - 搓冰机被动：仅当发生该机器颜色的普通同色双块匹配时，对应颜色段 -2；撞机本身的事件处理见其独立规则。
- **通关条件**：所有棋子全部消除完毕（成对消除）
- **限制条件**（已确认）：无全局步数限制（个别元素可带局部步数锁 stepLock，见 §2）；**有时间限制（秒）**——限时内消除全部棋子即通关，超时失败
  - 计时机制：**纯倒计时**（已按仓库修正）：**首个棋子被选中（首次操作）后开始计时**（CountLock "ProcOnGameBegin" 门控），此后持续倒计时，与操作次数/滑动距离无关
  - 限时数值来源（已按仓库修正）：**不在关卡 JSON 内**，由关卡上下文（LevelContext.baseTime，按难度 Normal/Hard/SuperHard 与关卡阶段配置换算）提供；10 秒低限警告；道具/复活可 ADD_TIME 加时
  - 限时量级：[已核对语料+配置表] 主线 A 表（Level.json）70–220 秒、中位 110；B/C 表 80–360 秒、中位 180（详见 §6）。最终限时由 `DynamicLevelTimeMgr.CalculateFinalLevelTime` 按 V1/V2 干预换算并 clamp（V1：min=max(MinSec, base×MinPercent) 取整十、max=base×MaxPercent 取整十；V2：按近期胜率在 base×ControlMin/Std/MaxPercent 之间插值，再按个位五舍六入到整十）
  - 可玩颜色（已按仓库修正）：**12 种可玩色**——RED/ORANGE/YELLOW/LIGHT_GREEN/LIGHT_BLUE/DARK_GREEN/CYAN/BLUE/PURPLE/MAGENTA(0-9) + BLACK(11) + WHITE(12)；枚举值 10 为已移除旧外观的空洞占位（不写入关卡）；单关颜色数（paletteSize）由难度配置取可玩色前 N 种；难度可整体循环换色（loopTime 偏移）
  - **【用户拍板 2025】无 NULL 色 / 颜色列表外一律不可用**：方块颜色只有上述 12 种；**不存在 NULL(-1) 玩法色**。color 缺失（NULL）或不在 12 色列表内的值，编关时一律视为不可用、不生成。语料（≤250 关）中现存约 1580 个 color 缺失块属历史数据（含双色配对底层/教学关），**不作为编关依据、不模拟**；生成关卡时每个块必须有 12 色之一（无色方块除外——顶层 color 省略 + MatchLockAbility.lockedColor 存真实色）。校验器 dual-mode：语料回归允许 NULL 色（仅警告），生成校验（--strict）报错

## 2. 特殊元素（待逐项核对，本节持续补充）
- [已确认] **无色方块（包装棋子）**：
  - 普通棋子上套一层无色包装；被包装时看不到真实颜色
  - 包装期**可以正常移动**，但**免疫一切消除**（与同色相邻也不消）
  - 解除条件：**全局计数**——场上每发生 1 次普通消除（任意一对普通棋子消除），该包装计数 +1，累计 N 次解除包装
  - 解除后显示**数据中预设的真实颜色**，恢复为普通棋子
  - 解除次数 N 由关卡配置，可较大（难度参数，无固定上限）
  - 关卡数据需含：位置 / 真实颜色 / 解除所需次数 N
- [已确认] **搓冰机**：
  - 外形：N 格长条，方向可配（上/下/左/右 单向 或 上+下/左+右 双向）
  - 结构：可削段 N-1 格 + 1 格底部占位（不可移动、不可单独消除）；整机 HP = N-1
    - **双向机型两端共享底部同一个占位格**（已确认）
  - 行为（已确认）：
    - 不可被玩家移动；占用格位阻挡拖拽放置（底部占位同样阻挡）
    - [已按仓库修正] **相撞判定**：拖拽中成功更新到当前格位、或松手复查时，棋子与机器**除底部占位外的任一颜色格四邻相邻**即进入优先级结算；不是起点选中瞬间的自动触发。
    - 相撞效果：仅**同色**棋子触发；机器 HP-1、**只从延伸方向末端(尖端)缩短一格**，该棋子**被消耗消失**，计 1 次消除事件（无色方块全局计数 +1）；异色棋子碰到无效（仅被挡）；**无色包装棋子（看不到颜色）撞到同样无效**（已确认）
    - **被动扣血（兼容规则）**：场上与机器同色的方块对消消失 → 对应颜色段**自动 HP-2、长度-2**；双向机器各段独立 HP，红对消扣红段、蓝对消扣蓝段
    - HP 扣完（含扣血溢出超过剩余 HP 的情形，一般不会出现）→ **整机连同底部占位一起消失**，格位变空可通行（已确认）
  - 配置项：颜色（可两端不同）/ 长度(HP) / 方向（单向或双向）/ 缩短方向
- [已确认] **双色方块**：
  - 结构：两个普通方块嵌套（外层色 A + 内层色 B，A 包 B 或 B 包 A 均可），**固定 2 层**，血量 = 2
  - 行为（已确认）：
    - 可移动，与普通棋子相同（拖拽、阻挡与当前格位结算规则一致）
    - 整体当作外层颜色(A)参与玩法；与外层同色的棋子**参与同色对消时剥壳**：另一枚 A 正常消失，它剥掉外层（HP 2→1）留下内层颜色(B)的普通单色方块
    - **剥壳后剩下的就是普通颜色方块**（已确认，2025）：内层 B 方块 = 普通单格棋子，不再带双色/剥壳属性；按普通规则继续消除（需再与 B 对消）
    - **每剥一层计 1 次消除事件**（无色方块全局计数 +1；整枚完全消除共 2 次）
  - 配置项：外层色 A / 内层色 B（谁包谁可配）
  - 与无色方块叠加（已确认）：无色包装套在最外层，解除包装前整体免疫；解除后按双色规则正常剥壳
- [用户拍板：按对齐规则定义（2025）] **装修区域（DecorationArea）**：
  - 外形：盖在 N×Z 矩形区域上的门/罩，门上有数字（HP）；**层级最高**；门下可配置棋子（**特殊元素也允许在门下**）
  - 行为（对齐确认）：
    - 不可移动、不参与消除；覆盖格**阻挡移动与放置**，未解锁时 = 被锁棋盘（拖动不能进入/穿过/停放在覆盖格）
    - **全局事件流扣血**：每发生 1 次消除事件 HP-1，HP=0 解锁：区域消失，覆盖格变回正常空格，露出下方棋子
    - **覆盖下全局被动机制仍生效**（已确认）：无色方块包装计数继续累计、搓冰机被动扣血(-2)照常触发；门下棋子自身能否移动/主动触发 [待与实现核对]
  - 配置项：HP / 覆盖尺寸 N×Z / 层级
  - 叠加规则（用户拍板 2025）：装修区域属**顶层元素**，**可以叠加**在**无色区域上方**（装修区域盖住无色区域）；与下方区域**不可叠放在一起**（编关时不生成此类配置；用户明确"做关卡时不要这么考虑"）
  - 与**下方区域是两个独立机制**：装修区域 = 全局事件计数解锁；下方区域 = 区域内清空触发
  - 与**门(Door)是不同元素**：装修区域不消耗棋子，只是覆盖+扣血解锁；门是“同色块进门被消耗”的出口（见下条）
  - 实现注记（源码）：仓库实体 DecorationAreaAbility（hp/width/height/layer）；监听 BLOCK_MATCH（普通两枚、ColorTrain、IceShaver 消耗/锤击）扣 HP——与以上玩法定义一致，事件来源范围以源码为准
- [用户暂不管（2025）] **门（Door）**：
  - Door 是独立机制，形状为 `D1/D2/D3 × T/B/L/R`，有 `color / withStar / stepLock / health`。门格阻挡普通放置；拖入与门同色、可匹配且未被锁/全冰覆盖的块，在方向与出口射线均合法时会被 `ConsumeBlock` 消耗并弹出，门本身不随该次消耗移除。
  - Door 的 `stepLock` 每个 `BLOCK_MATCH` 事件减 1；`health` 只在 `DoorConfig → Door.Health` 赋值，当前玩法代码未读取，语义 [待确认]。
  - `DoorConfig` 类存在，但 `LevelConfig` 顶层没有 `doors`，`EditorMgr` 保存也不写门，`GamePlayMgr.ReloadDoors` 只清空不生成；当前 JSON 持久化/加载链 [待确认]（编辑器历史与剪贴板可暂存 DoorConfig，不等于关卡落盘）。
- [用户拍板：按对齐规则定义（2025）] **冰冻方块**：
  - 结构：被冰封的普通棋子；血量 N 可配置（破冰所需消除次数）
  - **冰冻期间颜色可见**（冰块透明，与无色方块藏色不同）
  - 破冰前：**不可移动、不可消除、占用格位、阻挡移动与放置**——免疫一切消除（固定冰块障碍）
  - 破冰：与无色方块**同一全局事件流**、**各枚独立计数**，累计 N 次后破冰
  - 破冰后：变为**数据预设颜色**的普通棋子，按普通规则移动/消除
  - 嵌套范围（已确认）：可冻普通/双色/无色等元素；**冰冻为最外层壳**——破冰顺序按层级：先破冰，再按内部元素自身规则处理（如无色方块继续走自己的包装计数）
  - ⚠️ 实现差异提示（源码）：当前仓库实现为**区域制冰区**（`CellType.Ice` 连通组件 + `iceArea` 组件索引→整片层数；每个 BLOCK_MATCH 令全部存活冰区各 -1；全格覆盖时才锁定且默认隐藏真实颜色），**不是每枚独立计数**。以上为用户对齐的玩法定义；若要生成当前游戏可加载的关卡，需先与游戏实现对齐（或让游戏实现此规则）
- [已确认（按源码）] **冰面格子地形（CellType.Ice）**：
  - `cells[].cellType = Ice(1)` 是冰区的地形输入，负责生成冰面连通组件；当前源码没有“在冰面上滑行/改变拖拽规则”的实现。它与颜色筛选的 `cells[].color` 是同一 CellConfig 的两个独立字段。
- [已确认] **箭头方块（棋子移动轴向约束）**：
  - 给棋子设置"横向/纵向"箭头；**轴向约束**：横向=左右皆可、纵向=上下皆可，仅限该轴向
  - [已按仓库修正] 移动规则不变：仍是拖拽跟随；箭头只限制该拖拽簇能否在横/纵轴推进，不产生滑行或“路径中相邻即消”。
  - 消除规则不变：在一次当前格位结算中按四邻与其余条件匹配（箭头只约束移动）
  - 可配范围（已确认）：仅**可移动的棋子类型**——单色/无色/双色/冰冻(破冰后)/定时炸弹方块，以及**多格/特殊形状棋子（作为一个整体配置）**（已确认）
  - 生成注意：箭头进求解器（轴向可达性），须保证同色配对在各自轴向可达范围内可相遇
- [已按仓库修正] **手动制造机（ManualBlockDispenser）**：
  - 落地实体：`ManualBlockDispenser`（现有关卡 452 关中 82 关使用）；仓库另有自动制造机 AutoBlockDispenser（代码完整但现有关卡 0 使用，暂不定稿，见审计文档 §2.10）
  - 占位：机身若干格（LocalBodyGrids，默认 2×3，**可旋转 4 向**），1 个开口方向；占用的格位阻挡移动/放置；HP = 队列剩余数量；HP 归 0 → 机器连同未拖出方块一起消失，已拖出块留在棋盘
  - 交互（Manual，按仓库）：
    - **玩家从机器拖出**：preview 拖拽（TryBeginPreviewDrag），一次拖出队首那枚，拖完下一枚漏头
    - **拖出条件**：目标格可放置（PosPlaceable，含临时地形 CanPreviewUseTemporaryTerrain）；拖拽预览期间 StepLock 检查放宽（IsDraggingPreview 豁免）
    - **HP = 配置的方块数量**（remainingQueue.Count）；HP 归 0 时机器连同未拖出方块一起消失，已拖出留在棋盘
    - 产出块可带属性（无色 MatchLock / 步数锁 stepLock / 冻结等，按各元素规则）
  - [用户拍板 2025] **产出棋子可支持多格形状**，但尺寸必须**小于 3×3**。**判据已定 = C：包围盒不超出 3×3 范围（Rot0/90/180/270 全旋转下宽≤3 且高≤3）且总格数<9**（即允许 1×1/1×2/1×3/2×2/2×3/7/箭头/十字/倒三角/J 等所有 10 种合规标准形状，及不超 3×3 的自定义矩形；**拒绝 1×4、1×5 长条与 3×3 整块（9 格）**）。
  - ⚠️ 语料核对（452 关，82 台制造机共 597 个产出项）：**现有关卡产出项尺寸分布为**——B_1X1 42 / B_1X2 127 / B_1X3 133 / B_1X4 10 / B_1X5 2 / B_2X2 58 / B_2X3 17 / B_7 28 / B_ARROW 83 / B_CROSS 19 / B_DELTA 29 / B_J 32 / **custom 3×3 共 17 项**（lv_35/42/208/220/335/336/343/370/377/503）。
    - **按"包围盒 ≤2×2"判据**：只允许 B_1X1/B_1X2/B_2X2/B_ARROW——语料 310/597 项（52%）符合；B_1X3+、B_2X3、B_7、B_CROSS、B_DELTA、B_J、**全部 17 个 custom 3×3** 均会被排除（287 项，48%）。
    - **按"总格数 <9"判据**：12 标准形状全部符合（最大 B_2X3=6 格）→ 语料 580/597 项（97%）符合；仅排除 17 个 custom 3×3（9 格）。
    - ✅ **用户拍板 = 判据 C（2025）**：包围盒不超 3×3（全旋转宽≤3 且高≤3）且总格数<9 → 语料保留 **568/597（95.1%）**；仅拒绝 B_1X4(10) / B_1X5(2) / custom 3×3(17) 共 29 项，涉及 20 关。B_1X4/B_1X5 因任一边=4/5>3 超限（全旋转均超），3×3 整块因 9 格被拒。

- [已按仓库修正] **颜色筛选 = 格子颜色属性（cell.color）**：

## 3. 关卡数据格式（按仓库 LevelConfig 修正，11/12/13）
- 顶层字段：`cells / walls / blocks / entities / tracks / matchBlockOrder / iceArea`（文件内另有 `hash`）；**没有独立的 time / doors 字段**（限时来自关卡上下文，门不持久化于当前 JSON，见审计文档 §2.6）
- `cells`：`gridPos`(Vector2Int) + `color`(BlockColor，非 NULL=颜色筛选格) + `cellType`(Default=0 / Ice=1；Ice 格用于生成冰区连通组件)
- `walls`：`type`(结构墙 0-12 / 障碍墙 100-104) + `rot` + `gridPos` + `layer`（当前运行时只加载 CYCLE_PIPE，见 §2）
- `blocks`：`type / rot / color / gridPos / hasStar / withStar / hasCat / moveMode / stepLock / groupID / floor / keyLock / bombSecs / key / lock / withKey / customWidth / customHeight / layer / abilities`
- `entities`：`entityName / gridPos / layer / abilities`（区域类 / 冰铲 / 火车 / 制造机）
- `tracks`：轨道格坐标；当前用于 `TrackBuilder` / 带 `GridSelectAbility` 的普通块，ColorTrain 不读取该字段
- `iceArea`：`Dictionary<int,int>` 冰面**连通组件索引**→剩余层数（不是格子索引；组件由 `CellType.Ice` 生成）
- `matchBlockOrder`：消除顺序（见 §2.5）
- 序列化：`DefaultValueHandling.IgnoreAndPopulate` + `[IgnoreEmptyCollection]` → JSON 最小化（默认值省略）；`hash` 部分文件有（用途待确认）
- 提取物：规则实现细节 / 参数区间（棋盘尺寸、颜色数量、HP、N、限时）/ 现有关卡语料（452+ 关卡，AI 编关对齐基准 + 测试集）/ 编辑器校验逻辑

## 4. AI 编关约束（本工具派生需求）
- 生成流程：布局生成 → 合法性检查 → 可解性验证 → 难度评估（最少步数 + 限时换算）
- 时间限制：关卡数据是否含时间上限字段、限时与难度/棋盘规模的换算 [待确认]
- 元数据字段（标题/难度标签等）[待确认]
- **生成注意（双色方块）**：剥壳产生颜色转换（A→B），求解需纳入动态颜色配平——任何时刻在场颜色都应存在成对可消的路径，生成器须保证剥壳后颜色能达成全部消除
- **生成注意（箭头）**：箭头棋子只能沿轴向运动，求解器需建模移动方向约束；生成须保证同色配对在各自箭头轴向上可达
- **生成注意（炸弹）**：炸弹是硬时限约束——求解器状态需含炸弹剩余时间（含覆盖/冰冻暂停），生成须保证在炸弹时限内存在把炸弹消掉的可行路线，难度评估同时考虑炸弹时限与总限时

## 5.5 关卡范围与生成规模约束（用户拍板 2025）
- **有效关卡范围**：**≤250 号**（实际 223 关：编号 1-222 + 224，223 缺失）。250 号以后的关卡文件一律不看、不作为语料依据。
- **棋盘规模（生成约束）**：**棋盘格数不得低于 50**，暂无上限；但必须保证**棋盘连贯完整**（连通、无孤岛、无碎格）。
- **棋子数量（生成约束）**：**普通关 ≥15 对（30 枚）**；**难关、超难关 ≥18 对（36 枚）**。
- **求解器**（用户拍板 2025）：**完整状态搜索**；以下算子全部进入状态：拖拽移动（同层位移）/ 当前格位结算消除 / 制造机拖出 / 搓冰机消耗 / 火车端部消耗 / 区域解锁 / 双色剥壳颜色转换 / 绑定体整体移动 / 炸弹倒计时（含暂停）/ stepLock 解锁 / 无色区域边界判定。
- **求解器算法/顺序/入口（拍板 2025）**：分阶段——先可解性 BFS（状态规范化去重）、再最少步数 A*（对称剔除/启发式）；目标=可解性+最少步数都要；算子落地 5 阶段=基础对消(含双色剥壳/无色/绑定/箭头)→制造机→区域(装修/下方/无色)→火车→炸弹/stepLock；入口=先跑现有 223 关做正确性/性能基线 + 最少步数分布、再接生成器。设计文档 `docs/solver-design.md`。
